# Week 12 — AI Engineering: Chapter 6 (Agents) — Build & Audit
**Date:** July 19, 2026
**Chapters/resources covered:** Chapter 6 — Agents, hands-on build (Tools, Function Calling, Planning Granularity, Tool Selection, Reflection & Error Correction, Failure Modes & Evaluation). Memory covered conceptually, not yet implemented.
**Status:** IBOV Analysis & Recommendation Agent built, tested (32/32), v1 (fixed pipeline) vs v2 (agent loop) compared live on real tickers, documented, committed same day.

## 10 observations I made (not a summary — what stood out)
1. The most important design decision I made before writing any tool code: compute tools take a `ticker`, hit a server-side cache, and return the already-computed result — never a raw price array or volume list back into the model's context. Raw data in context isn't just wasteful, it's an invitation for the model to do its own math on it.
2. I had conflated cache with "saving tokens." It's not that — it's a data-boundary control. The cache exists so a fetch tool and a compute tool that both need the same ticker's data don't hit the API twice and don't disagree with each other mid-conversation. Token cost is a side effect, not the reason it exists.
3. I also had conflated who decides which tools to call. `agent.py` doesn't pick tools — it only runs the loop (call the API, check for `tool_use`, execute the tool, send back `tool_result`, repeat until the model stops asking). Every tool-selection decision is the model's, not the orchestration code's.
4. v1 (the fixed pipeline: screener.py → synthesis.py → main.py) has zero tools. It's not "a simpler agent" — by the chapter's definition it isn't an agent at all. Building both versions side by side made that distinction concrete instead of definitional.
5. Auditing tool selection surfaced a real distinction I hadn't separated before: for ITUB4 (a bank), the agent read `missing_fields` on the fetched fundamentals and skipped calling `compute_debt_to_ebitda` entirely — 6 calls, 0 errors. That's the agent anticipating a call would fail and avoiding it, not recovering from a failure. "Never tried" and "tried and recovered" look identical in a call count and very different in a trace.
6. The trace is the only thing I actually trust now. On the MGLU3 run, the model's final answer narrated a conditional step it never executed — the tool-call log (`runs.jsonl`) showed it didn't happen. The model's own summary of what it did can diverge from what it did, even when every individual tool result was correct.
7. Same underlying numbers, different verdicts. v1 and v2 share `indicators.py`, so the math is identical — but v1's hard rule-based gate and v2's LLM synthesis disagreed on VALE3 (v1: Avoid, v2: Neutral-leaning-Watchlist). A hard gate forces a binary cutoff; an LLM sitting on the same numbers can anchor differently and land in the ambiguous middle. Neither is "more correct" by construction — they fail differently.
8. The cost gap between the two versions is not subtle: v1 is 1 LLM call total, v2 is 12 calls per ticker (7 tools plus reasoning plus synthesis). For most tickers they reached the same shortlist decision. The 12x only earned its keep on the one ticker where v1's hard gate was structurally wrong (see observation 9).
9. I found a real structural blind spot and deliberately didn't patch it: ITUB4 (a bank) has null `totalDebt` / `ebitda` in the brapi fundamentals payload, so any debt/EBITDA filter fails for the entire banking sector by construction — not because of a bug, but because debt/EBITDA isn't a meaningful ratio for banks in the first place. The right move was to flag it in the audit checklist as a known sector-blindness, not to quietly special-case banks in the code.
10. Memory finally clicked apart into two separate things. Within a single agent run, "memory" isn't a feature at all — it's just the stateless API plus the client resending a growing `messages` array each turn, the same mechanism already powering the tool-calling loop's round trips. Real memory — the thing the chapter is actually about — means state persisting across separate process runs. And storage format (files, a DB, RAG) is a decision that's independent from retrieval strategy (inject everything vs. selective retrieval) — I used Claude's own file-based memory system as a live example of that split while we talked about it.

## What I still didn't understand
- I understand the storage-vs-retrieval split conceptually now, but I don't have a built version to check it against yet — the agent doesn't persist anything across runs today (no Memory section implemented). I don't have a felt sense for when selective retrieval actually earns its complexity versus just injecting everything, since I've only seen it discussed, not hit the wall where inject-everything stops working.
- `log_run` doesn't record token usage, so I can describe the 1-call-vs-12-call cost gap in call counts but not in actual spend. I don't yet know if that gap is trivial or meaningful in real money at IBOV scale.
- Whether v1's zero-tool pipeline should really be called "not an agent" or "a degenerate one-call agent" still feels like a definitional edge case to me, not a settled distinction.

## How this changes how I think about product
- Observation 6 (trace vs. narrative) is a governance point I hadn't internalized before building this: you cannot audit an agent by reading its final answer. If I ship an agentic feature as a PM, the trace needs to be a first-class, inspectable artifact — not a debugging afterthought — because the model's self-report is not reliable evidence of what it did.
- Observation 7 and 8 together are a concrete version of a build/buy tradeoff I'll actually face: a deterministic pipeline is cheaper, auditable, and consistent, but it's only as good as its hardest-coded gate. An agent costs more (in this case, an order of magnitude more) and its value is concentrated in the specific cases where rigid rules break — which means the decision to use an agent at all should be scoped to "where do we expect the rules to break," not applied by default because agents are the more capable-sounding option.

## Open question
- Observation 9 (the bank sector-blind filter) is still unresolved in a way that bugs me: is the right fix to add a bank-specific ratio so the filter stops being blind, or is "flag it and don't silently route around it" actually the more honest long-term behavior for an agent — i.e., should agents be allowed to surface "I don't have a valid check for this case" as a first-class output, instead of every gap eventually getting patched away?
