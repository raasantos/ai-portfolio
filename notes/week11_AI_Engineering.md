## 10 observations I made (not a summary — what stood out)
1. Agents can recognize and act upon their environment.
2. When designing an agent, the environment will define the tool set to be implemented. The reverse is also true: if an agent built for one environment gets reused in a different one, the tool set it was built with limits what it can do there. (One thing I added after review: what counts as "the environment" is a choice I make, not a fixed fact. My Instagram agent shows this. If I had scoped the environment as "social media marketing" instead of just "Instagram," LinkedIn would be inside that scope too. The only thing limiting it to Instagram is that I only built a tool for posting there.)
3. Self-critique and error correction don't mean the agent will actually improve. The critique is just more text from the same model, so it can miss the same things the original plan missed. That's why Reflexion uses a separate evaluator and self-reflection module instead of having the agent critique itself.
4. I designed and implemented an Instagram Publication agent. Real tool inventory: Trello read (understand task), create images, update task, post on Instagram, close task. Trello read is knowledge augmentation. Create images is capability extension. Update task, post on Instagram, and close task are all write actions. Half the inventory is write actions, and "post on Instagram" is the highest risk one since it's irreversible once public. Right now it has no approval gate. That's a decision I need to make on purpose, not leave as a default.
5. When an AI evaluates and reflects on a plan, that evaluation itself needs prompt engineering, heuristics, and some kind of scoring to work well. The book's terms for this: heuristics and AI judge (or specialized scorer) are the two validation methods, and reflection can be self-critique by the same agent or a separate scorer module.
6. Tools extend an agent's knowledge, capabilities, and actions. The book's three categories: knowledge augmentation, capability extension, write actions.
7. Agents have their own failure modes, caused by planning, tool execution, and efficiency.
8. Evaluating agent failures is different from evaluating a regular AI application because an agent makes a chain of decisions instead of one. I need to check how it thinks (plans), executes (uses tools), and follows rules (constraints) separately, not just check the final output. Same as briefing a person for a job, the instructions have to be clear, which is why understanding what a task actually is (goal + constraint) matters so much.

## What I still didn't understand
- ~~When implementing agents using tools such as n8n, could the nodes implemented be considered the toolset of that agent?~~ This depends on the node type. Nodes that call an external system to do something, like Trello, image generation, or posting to Instagram, are tools. Logic nodes like if, switch, or merge are not tools, they're control flow (sequential, parallel, if, loop), which is a separate concept.
- ~~ChatGPT Desktop / Claude Desktop are agents with plenty of tools available, expanding as they understand more use cases. They weren't born with a "text generator" tool, text generation is the base model's native capability, not a tool. What they've gained since are write-action tools (email, Notion, Slack). Would this be a multi-purpose agent?~~ Yes, and it's the same tension Tool Selection talks about. More tools give more capability, but they get harder to use well, same as a person trying to master too many tools, and more tool descriptions compete for context space. This doesn't break the "environment comes first" idea, it just means the environment was defined very broadly from the start ("general assistant for knowledge work"), and tools keep filling that space over time.
- ~~How can a PM influence or define agent planning and task execution? How to reduce the paths an agent can take?~~ Not only guardrails after the fact. Real levers: defining the task (goal + constraint), designing the tool inventory (fewer tools means fewer possible paths), choosing which control flows to allow, deciding plan granularity, reviewing prompt and tool description quality, setting validation gates, and choosing which of the 4 reflection moments to use. Most of this influence happens before the agent starts reasoning. It shapes the space instead of filtering the output afterward.
- ~~How does using tuples (task, tool inventory) help?~~ A plan is only valid or invalid relative to a specific tool inventory. Fixing the task and only changing the inventory, or the other way around, is what lets you tell whether a result changed because of the task or because of the inventory. Same idea as an ablation study, applied to a fair comparison.
- Still open: building real work applications, how do I separate what counts as an agent from an assistant? My working guess after this review, not something from the book, is that it's about how much write action autonomy there is, not a hard category. An assistant gives a recommendation and the human executes it. An agent executes the write action itself. AI that only analyzes data is assistant-like. AI that buys the cheapest product on its own is agent-like.

## How this changes how I think about product
- Before I had trouble telling assistant and agent apart. Now I have a working guess (how much write action autonomy), but I haven't tested it against the rest of the book yet.
- I didn't know how to think about reflection. I would have just called it "eval" without realizing it can happen in 4 different moments.
- I used to think AI was only solving pieces of a problem, automating repetitive actions. The real shift is that agents can make autonomous decisions with write actions, and that's where the real risk is: wrong parameters, compound error, an agent thinking it's done when it isn't.
